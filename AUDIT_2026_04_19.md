## Находки по модулям

### execution/

**A1 🔴 Дубликат класса `ExecutionGovernor` — реальный + stub**
- Реальный: `src/okx_nft_bot/execution_governor.py`. Содержит `reconcile_active_offers`,
  `check_live_submit_allowed`, состояние в SQLite через PositionState.
- Stub: `src/okx_nft_bot/execution/governor.py:90` — класс с тем же именем, но asyncio-очередь,
  фейковые tx hash (`f"0x{request.request_id}"` на строке 300), комментарий `# Implementation needed`
  на строке 289, in-memory state, unbounded `execution_history` список (memory leak).
- Stub импортируется только dead-v2 кодом (`cli_v2.py`, `main_v2.py`, `parasite_hunter_v2.py`).
- Рабочий код (`counterbid/engine.py`, `undercutter/engine.py`, `mass_offer/engine.py`,
  `execution_cli.py`, `execution_daemon.py`, `parasite_hunter.py`) импортирует корректный.
- **Риск**: если в будущем кто-то случайно сделает `from okx_nft_bot.execution.governor import ExecutionGovernor`
  вместо `from okx_nft_bot.execution_governor import ExecutionGovernor`, получит заглушку. Имена классов
  идентичны → IDE-autocomplete может подменить. Рекомендация: удалить `execution/governor.py` или
  переименовать класс (например, `ExecutionGovernorV2Stub`).
- **Местоположение**: `src/okx_nft_bot/execution/governor.py:90`

**A17 🟡 Stub `ExecutionGovernor` имеет unbounded `execution_history`**
- `src/okx_nft_bot/execution/governor.py:100` — `self.execution_history: List[ExecutionResult] = []`,
  появляется в `_execute_request` (строка 205). Никакой очистки нет.
- Если stub будет активирован (сейчас — нет), утечка памяти на каждом запросе.
- Dead code, но фиксим заодно с A1.

### mass_offer/

**A3 🔴 Stale Seaport counter при множественных движках на одном кошельке**
- `src/okx_nft_bot/mass_offer/engine.py:218` — `counter = get_counter(account.address, rpc_url=rpc_url)`.
  Читается один раз в начале прогона, далее `counter += 1` локально (строка 247).
- Тот же кошелёк (`buyer_wallet_private_key`) используется parasite_hunter, undercutter,
  offer_blaster, counterbid — каждый читает свой локальный counter в своё время.
- Если параллельно работают 2+ движка или юзер вручную делает `incrementCounter()` между
  стартом `MassOfferEngine.run` и сабмитом последнего оффера — оффер получит stale counter
  и будет отвергнут контрактом (invalid order).
- **Фикс**: либо (а) читать counter перед каждым оффером (дорого — RPC вызов), либо
  (б) вести локальный инкрементальный счётчик в SQLite с атомарным next-counter'ом и
  периодически синкать с on-chain.

**A15 🟡 `token_id=0` трактуется как collection-offer sentinel**
- `src/okx_nft_bot/mass_offer/engine.py:322` — `is_collection_offer = not token_id or str(token_id) in ("", "0", "col", "collection")`
- Для коллекций, где tokenID нумеруется с 0 (редкость, но встречается в ERC-1155 / некоторых
  ERC-721), это вызовет непреднамеренный collection-offer вместо item-offer → большая экспозиция.
- **Фикс**: использовать отдельный sentinel (например `None` или `"*"`), не перегружать 0.

### undercutter/

**A5 🟠 Live-оффер может остаться с "dryrun-" order_hash при неполном ответе submit_offer**
- `src/okx_nft_bot/undercutter/engine.py:243-248` — новый хеш всегда генерится как
  `"dryrun-" + hash(...)`, затем в live-ветке строка 302 заменяется на `submit_result["offer_id"]`.
- Если `submit_result.get("offer_id")` пуст (None/""), `str(...)` даст `"None"` или пустую
  строку → `new_order_hash` с префиксом "dryrun-" остаётся.
- `execution_governor.py:145` фильтрует `startswith("dryrun-")` из `local_live` → live оффер
  становится невидим для reconcile. Potential orphan в state.
- **Фикс**: явно требовать непустой offer_id от submit_offer, раз оффер реально ушёл.
  Если offer_id пуст — не писать в state вообще (reconcile подтянет).

**A6 🟠 Retire-before-submit при DEFENSE — окно без защиты**
- `src/okx_nft_bot/undercutter/engine.py:295-301` — сначала
  `_retire_previous_offer_for_defense` отменяет старый оффер on-chain, затем
  `self.offer_client.submit_offer(...)` сабмитит новый.
- Если submit падает (сеть, 429, signature) — старый уже отменён, защиты нет до следующего
  cycle. При `undercut_interval_seconds=30` это до 30 секунд без защиты от агрессивного парасайта.
- **Фикс**: сабмитить новый первым, потом отменять старый. Стандартный паттерн "new-then-retire"
  у OpenSea и ME.

**A18 🟡 `_order_hash` не детерминирован (использует `str(dict)`)**
- `src/okx_nft_bot/undercutter/engine.py:383` — `seed = f"{collection}:{price}:{action_type}:{preview_payload or {}}"`
- `preview_payload` — dict. `str(dict)` зависит от порядка ключей (в Python 3.7+ сохраняется
  порядок вставки, но разные источники могут собрать payload с разным порядком).
- Не бизнес-критично (хеш только для dry-run), но ломает идемпотентность и тесты.
- **Фикс**: `json.dumps(preview_payload, sort_keys=True)`.

**A8 🟠 `UNDERCUTTER_MIN_PRICE_BNB` — safety floor только для undercutter**
- `src/okx_nft_bot/undercutter/engine.py:207` — env-driven минимум 0.0001 BNB применяется
  только в `_apply_action` UndercutEngine.
- `offer_blaster.py`, `mass_offer/engine.py`, `parasite_hunter.py` (strategy section) — нет
  аналогичного guard'а. Консистентности защиты от "dust offer" по всему боту нет.
- Пересекается с K7 (удалённый `min_listing_price_bnb` в parasite_hunter).
- **Фикс**: вынести min-price guard в `ExecutionGovernor.check_live_submit_allowed` — единая точка.

### clients/http.py

**A12 🟡 Hardcoded `rate_limit_per_sec=5.0` в buyer/offer_blaster**
- `src/okx_nft_bot/sniper/buyer.py:271,549` и `src/okx_nft_bot/sniper/offer_blaster.py:275` —
  создают локальный `StdlibHttpTransport(..., rate_limit_per_sec=5.0)` для RPC/вспомогательных вызовов.
- Не критично (это не OKX API calls), но должно быть настраиваемо через `settings`.

**A13 🟡 `get_okx_global_limiter` race при изменении rate**
- `src/okx_nft_bot/clients/http.py:44-52` — если второй вызов приходит с меньшим rate,
  создаётся **новый** `RateLimiter`, старые instances (у `OKXMarketplaceClient.transport`) 
  продолжают держать ссылку на прежний (более быстрый).
- Практически settings.okx_rate_limit_per_sec один на процесс — триггерится редко.
- **Фикс**: менять атрибуты существующего limiter вместо создания нового; либо сделать его
  полностью immutable и перезапускать процесс при изменении.

### config.py

**A4 🟠 `DRY_RUN=""` тихо превращается в `dry_run=False`**
- `src/okx_nft_bot/config.py:239` —
  `dry_run=_optional_bool(os.getenv('DRY_RUN')) if os.getenv('DRY_RUN') is not None else True`
- `os.getenv('DRY_RUN')` возвращает `""` (не `None`) если переменная задана пустой.
  `_optional_bool("")` возвращает `False` → `dry_run=False`.
- **Сценарий**: оператор правит `.env`, случайно оставляет `DRY_RUN=` (без значения) →
  бот уходит в live-режим без предупреждения.
- Тот же паттерн для `MASS_OFFER_DRY_RUN` (строка 246).
- **Фикс**: явно проверять `if env_value and env_value.strip()`; по умолчанию — True.

**A19 🟡 Дивергенция defaults: dataclass vs load_settings**
- `Settings.okx_rate_limit_per_sec = 1.5` (dataclass default, строка 35).
- `load_settings` использует `'3.0'` как env default (строка 188).
- Если кто-то инстанцирует `Settings(...)` напрямую (например в тестах), получит 1.5 — другое
  поведение чем прод. Такое же расхождение может быть и по другим полям.
- **Фикс**: синхронизировать defaults в одном месте (например через модуль-константы).

### storage/

**A11 🟡 Непоследовательные SQLite-паттерны между stores**
- `storage/sqlite.py`: `sqlite3.connect(db_path)` без timeout/WAL. Per-call connection.
- `storage/offers_store.py`: то же самое.
- `storage/fraud_store.py:27-30`: caller-managed connection (передаётся как аргумент в методы).

- Только `state.py` защищён от блокировок при многопроцессном доступе. Остальные могут
  выдать `SQLITE_BUSY` при одновременной записи.
- **Фикс**: единый helper `_connect()` в базовом классе Store, WAL везде.

**A10 🟡 `PositionState._db_lock` — dead code**
- `src/okx_nft_bot/undercutter/state.py:87` — `self._db_lock = __import__('threading').Lock()`.
- Grep показывает использование 0 раз (кроме самого объявления).
- WAL + busy_timeout покрывают конкурентность, lock ненужен.
- **Фикс**: удалить строку 87.

### analytics/

**A7 🟠 `detect_spreads` не нормализует валюты**
- `src/okx_nft_bot/analytics/cross_market.py:137` —
  `reference_price = latest_listing_price or floor_price or latest_sale_price` (в native currency
  каждого маркета).
- Строки 167-168: `min`/`max` по разным маркетам для поиска buy/sell сторон.
- Строки 181-190: `buy_price` и `sell_price` записываются как float без явного преобразования.
- Если OKX даёт листинг в BNB, OpenSea — в ETH, обычное сравнение `buy_price < sell_price`

  её не использует для проверки консистентности.
- **Фикс**: либо (а) считать спред только когда `buy_side.currency == sell_side.currency`,
  либо (б) конвертировать в общий знаменатель (USDT) через price oracle.

## K5 verification addendum (2026-04-20)

Live probe of OKX API (`/api/v5/mktplace/nft/markets/offers` and
`/collection-offers`, chain=bsc, status=active) returned the
`protocolData.parameters.orderType` (the Seaport contract enum) for three
cases:

| Case                                    | amount  | `itemType` (consideration) | `orderType` |
|-----------------------------------------|---------|----------------------------|-------------|
| Parasite single collection offer        | 1       | 4 (ERC721_WITH_CRITERIA)   | **2** (FULL_RESTRICTED) |
| Our 10× collection offer                | 10      | 4 (ERC721_WITH_CRITERIA)   | **3** (PARTIAL_RESTRICTED) |
| Parasite ERC1155 item offer             | 50      | 3 (ERC1155)                | **3** (PARTIAL_RESTRICTED) |

Pattern: `orderType=2` (FULL_RESTRICTED) for single-unit atomic fills;
`orderType=3` (PARTIAL_RESTRICTED) when `startAmount>1` (partial fills
allowed). Both values are accepted by OKX — the distinction is Seaport
semantics, not marketplace gate.

`_build_offer_payload` (signing/seaport_signer.py:287) hardcodes
`startAmount="1", endAmount="1"` and a single consideration item → this is
the single-unit atomic case → `FULL_RESTRICTED (2)` is semantically
correct.

**Decision**: the WIP change (orderType 2→3) is NOT needed for
`_build_offer_payload` as currently written. Current committed code (2) is
consistent with live OKX orders of the same shape. WIP intentionally
discarded. If in the future the builder grows batch/partial support, flip
to 3 at that point.
