## 1. 🔴 BUG

### BUG-1: `audit_integrity` сбрасывает валидное ETH-состояние после A9

**Файл:** `src/okx_nft_bot/undercutter/state.py:781-787`

**Что:**
```python
if raw_reconcile_chain and raw_reconcile_chain.strip().lower() != "bsc":
    notes.append(f"execution_runtime_state.last_reconcile_chain={raw_reconcile_chain!r} cleared")
    with self.conn:
        self.conn.execute("UPDATE execution_runtime_state SET last_reconcile_chain=NULL ...")
```

`audit_integrity()` считает любой не-"bsc" chain невалидным и зануляет поле, хотя
после A9 (commit 08133d5) поддерживается `eth` (см. `SUPPORTED_EXECUTION_CHAINS`
в `config.py:167`). После одного ETH-реконсайла следующий вызов `audit-state`
сотрёт корректный timestamp, и `execution_daemon` начнёт дублировать полные
реконсайлы ETH-ветки.

**Последствие:** ложно-позитивный `notes` в audit-отчёте + потеря последнего
timestamp ETH-реконсайла → спам RPC/API ETH-ветки при каждом рестарте.

**Фикс:** в проверке использовать `from okx_nft_bot.config import SUPPORTED_EXECUTION_CHAINS`
и сравнивать `raw_reconcile_chain.strip().lower() not in SUPPORTED_EXECUTION_CHAINS`.

**Приоритет:** P0 (блокирует работу A9-фичи, которая только что задеплоена).

### BUG-2: `SQLiteStore` / `OffersStore` без WAL — риск `database is locked`

**Файлы:**
- `src/okx_nft_bot/storage/sqlite.py:19-74` (`SQLiteStore._init_db`)
- `src/okx_nft_bot/storage/offers_store.py:37-66` (`OffersStore._init_db`)

**Что:** оба хранилища открываются `sqlite3.connect(db_path)` **без**
`PRAGMA journal_mode=WAL` и без `busy_timeout`. Сравните с
`undercutter/state.py:93-94` и `sales_stream.py:163-164`, где WAL+busy_timeout
явно выставлены.

`data/okx_nft_bot.sqlite3` пишется из `Monitor.run_live_cycle` (main
container) и, судя по CLI-командам, читается из других процессов (healthcheck,
`cli` subcommands в telegram_bot). Без WAL writer-lock блокирует всех
читателей; при одновременных writer'ах — `sqlite3.OperationalError: database is locked`.

**Последствие:** периодические падения цикла или лагающие команды в
Telegram-bot при активной записи. Данные не теряются (транзакция просто
откатывается), но каждый инцидент требует ретрая и отображается в логах
как exception.

**Фикс:** в `_init_db` обоих классов добавить перед `CREATE TABLE`:
```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA busy_timeout=5000")
```

**Приоритет:** P1 (падает периодически, маскируется exception-логгированием).
Повышается до P0 если `cli.py` healthcheck команды ходят по этой же БД
из отдельного процесса.

## 2. 🟠 RISK

### RISK-1: Race nonce между `buyer` и `_cancel_onchain_seaport`

**Файл:** `src/okx_nft_bot/counterbid/okx_api.py:1474`

**Что:** `nonce = w3.eth.get_transaction_count(account.address)` — **без** `"pending"`,
**без** локов, **без** кэша. Параллельно `buyer.py:478-484` держит свой in-memory
`_nonce_cache` с `self._lock`, но это только внутри одного процесса. Между
контейнерами ни общего лока, ни общего кэша нет. Если `execution` контейнер
отсылает `incrementCounter` / `cancel` одновременно со `sniper` контейнером
(`buyer.execute_buy`) на один private_key — получают одинаковый nonce → одна
транзакция отклонится с `nonce too low`.

**Последствие:** потерянный cancel или потерянный buy при конкурентном доступе.
Не фатально, но требует ручного ретрая; при активном undercutter цикле
вероятность реальна.

**Фикс:** `w3.eth.get_transaction_count(addr, "pending")` минимум; optimal —
перенести аллокацию nonce в `PositionState` по аналогии с `allocate_seaport_counter`
(SQLite-atomic `BEGIN IMMEDIATE`, тот же шаблон).

**Приоритет:** P1.

### RISK-2: `buyer._nonce_cache` не персистится

**Файл:** `src/okx_nft_bot/sniper/buyer.py:173, 478-484`

**Что:** `self._nonce_cache: dict[str, int] = {}` живёт в памяти процесса.

с прошлого запуска.

**Фикс:** переход на ту же SQLite-allocation схему из `PositionState`;
либо минимум — всегда использовать `"pending"` в `get_transaction_count`.

**Приоритет:** P1 (вместе с RISK-1).

### RISK-3: Хардкод `BSC_RPC` без failover

**Файл:** `src/okx_nft_bot/signing/seaport_signer.py:28`

**Что:** `BSC_RPC = "https://bsc-dataseed.binance.org/"` — используется для чтения

per-offer, так что это блокирует каждый submit.

**Фикс:** список RPC с round-robin или failover, аналогично `_CHAIN_RPCS`
в `execution_governor.py:25-30` (там уже есть `bsc`, `eth`, `polygon`, `arbitrum`).
Простейший вариант — reuse `_CHAIN_RPCS` и пробовать каждый до первого успеха.

**Приоритет:** P1.

### RISK-4: `parasite_hunter` обходит shared HTTP transport для balanceOf

**Файл:** `src/okx_nft_bot/sniper/parasite_hunter.py:2673`

**Что:** ERC20 balance читается через `urllib.request`, минуя
`StdlibHttpTransport` и его rate-limiter. Это не проходит через глобальные
OKX/RPC rate-limiters и не участвует в circuit-breaker.

**Последствие:** потенциальный overshoot на RPC провайдере при частых
balance-проверках; не попадает в метрики; расходится с нагрузкой,
которую rate-limiter пытается сдерживать.

**Фикс:** заменить на `w3.eth.call` через общий `_get_web3_for_chain` helper,
либо на `StdlibHttpTransport` с JSON-RPC payload.

**Приоритет:** P2.

### RISK-5: Относительные пути для кэшей

**Файлы:**
- `src/okx_nft_bot/counterbid/okx_api.py:175` — `Path("data/project_id_cache.json")`
- `src/okx_nft_bot/sniper/offer_blaster.py:65` — `Path(os.getenv("EXECUTION_DB_PATH", "./data/execution.sqlite3"))`

**Что:** относительные пути зависят от CWD процесса. Если контейнер запущен

**Последствие:** расхождение state между контейнерами при неверном WD;
project_id кэш не будет переиспользован.

**Фикс:** проваливать через `settings.data_dir` (или аналог) и использовать
абсолютный путь.

**Приоритет:** P2.

### RISK-6: Три контейнера × локальный rate-limiter = 3× overshoot (Q1)

**Файлы:** распределённо — все потребители OKX (`clients/okx.py`, `counterbid/okx_api.py`,
и т.д.). Ранее отмечено в KNOWN_ISSUES.md как Q1.

**Что:** `OKX_RATE_LIMIT_PER_SEC=0.3` применяется per-process. Контейнеров 3
(main / exec / telegram), => реальный rate ≥ 0.9 RPS → 429 (50011) в логах на ~40%
запросов.

**Последствие:** падение успешности submit/cancel; retry logic маскирует, но
жжёт window backoff.

**Фикс:** либо общий Redis/sqlite rate-limiter (IPC), либо уменьшить
`OKX_RATE_LIMIT_PER_SEC` в 3 раза на процесс, либо переехать на отдельный
IP для самого критичного (execution) контейнера.

**Приоритет:** P1 (фича-ухудшающе, регулярная деградация).

### RISK-8: `get_okx_global_limiter` сбрасывает `_last` при re-create

**Файл:** `src/okx_nft_bot/clients/http.py:44-52`

**Что:**
```python
def get_okx_global_limiter(rate_per_sec: float) -> RateLimiter:
    global _okx_global_limiter
    with _okx_global_lock:
        if _okx_global_limiter is None:
            _okx_global_limiter = RateLimiter(rate_per_sec)
        elif rate_per_sec < _okx_global_limiter.rate_per_sec:
            _okx_global_limiter = RateLimiter(rate_per_sec)
    return _okx_global_limiter
```

При создании второго `OKXMarketplaceClient` с более медленным rate лимитер
**пересоздаётся** — но у нового объекта `_last = 0.0`. Первый запрос после
пересоздания пройдёт без wait (elapsed будет огромным), что даст мгновенный
burst и обойдёт rate-limit.

**Последствие:** если бот периодически пересоздаёт клиенты (например, на
каждый cycle в каком-то CLI), burst-запросы могут спровоцировать 429.
На практике клиенты обычно живут весь процесс, так что риск низкий.

**Фикс:**
```python
elif rate_per_sec < _okx_global_limiter.rate_per_sec:
    prev_last = _okx_global_limiter._last
    _okx_global_limiter = RateLimiter(rate_per_sec)
    _okx_global_limiter._last = prev_last
```

**Приоритет:** P2.

### RISK-9: `raw_events` таблица без unique-констрейна — дубли при partial-failure

**Файл:** `src/okx_nft_bot/storage/sqlite.py:22-30, 76-84`

**Что:** таблица `raw_events` имеет только `AUTOINCREMENT id` как PK. В
`live_cycle.py:104-120` `insert_raw_events` вызывается на каждой странице,
а `state.set(cursor)` — только после цикла. Если insert успешен, но прогон
упал до `state.set`, при следующем запуске те же сырые события
вставятся заново.

`normalized_events` защищён unique `event_id` PK, так что дубли в raw
не трогают нормализованный поток. Но raw-таблица раздувается бесконечно
при регулярных частичных failures.

**Последствие:** рост БД, ухудшение query-latency на анализе raw_events.

**Фикс:** добавить UNIQUE(source, content_hash) или просто периодический
VACUUM + cleanup старых raw_events через retention policy.

**Приоритет:** P2.

## 3. 🟡 SMELL

### SMELL-1: Хрупкий паттерн `"0x" + sig.hex()` в 4 местах

**Файлы:**
- `src/okx_nft_bot/signing/seaport_signer.py:342`
- `src/okx_nft_bot/counterbid/okx_api.py:935`
- `src/okx_nft_bot/sniper/offer_blaster.py:606`
- (4-й — в `signing/opensea.py` по заметкам, проверить в v2 аудите)

**Что:** В `eth-account >= 1.0` (наш pin `>=0.11,<1`) `signed.signature` — `HexBytes`,
и `.hex()` возвращает строку **без** `0x`-префикса в текущей версии, но в
`eth-account 1.0+` и в некоторых будущих `HexBytes` версиях поведение
меняется. Конкатенация `"0x" + signed.signature.hex()` даст `"0x0x..."`
при обновлении зависимости.

**Последствие:** полный refusal всех подписей при minor-upgrade `eth-account`
или `hexbytes`.

**Фикс:** `sig_hex = signed.signature.hex(); sig_hex = sig_hex if sig_hex.startswith("0x") else "0x" + sig_hex`
или `to_hex(signed.signature)` из `eth_utils`.

**Приоритет:** P2.

### SMELL-2: `.isdigit()` на числовых полях

**Файлы:**
- `src/okx_nft_bot/sniper/parasite_hunter.py:3339`

### SMELL-4: `_salt_counter` module-level, per-process only

**Файл:** `src/okx_nft_bot/signing/seaport_signer.py:11-13`

**Что:** `_salt_counter` с `threading.Lock`, salt per-process. Защита от

**Последствие:** косметика; риск регрессии при рефакторинге.

**Фикс:** комментарий `# salt entropy: os.urandom(8) | counter — don't reduce randomness below 8 bytes`.

### SMELL-5: `_fetch_order_params` — O(n) скан для каждого cancel

в `run_cycle` (scope: один цикл) и передавать словарь в `_fetch_order_params`.

**Приоритет:** P2.

### OPT-2: Фиксированный 1с retry-sleep без jitter
